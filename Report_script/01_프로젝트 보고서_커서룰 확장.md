# 커서룰 생성 방법
_Exported on 5/18/2026 at 15:15:23 GMT+9 from Cursor (3.4.17)_

---

**User**

커서룰 만드는 방법 알려줘. 코드에 업데이트는 하지말고.

---

**Cursor**

커서룰은 프로젝트 안에 `.cursor/rules/*.mdc` 파일로 만들면 됩니다. 코드 업데이트 없이 직접 만들 때는 이런 구조를 쓰면 돼요.

```markdown
---
description: 이 룰이 무엇을 안내하는지 짧게 설명
globs: **/*.ts
alwaysApply: false
---

# Rule Title

- 여기에 Cursor Agent가 따라야 할 프로젝트 규칙을 적습니다.
- 짧고 구체적으로 작성하는 게 좋습니다.
- 가능하면 좋은 예시/나쁜 예시를 포함합니다.
```

전역으로 항상 적용하려면 `alwaysApply: true`를 쓰고 `globs`는 생략해도 됩니다.

```markdown
---
description: 프로젝트 공통 개발 규칙
alwaysApply: true
---

# Project Rules

- 기존 코드 스타일을 우선 따른다.
- 불필요한 리팩터링은 하지 않는다.
- 테스트가 있는 경우 변경 후 관련 테스트를 실행한다.
```

특정 파일에만 적용하려면 `globs`를 지정합니다.

```markdown
---
description: React 컴포넌트 작성 규칙
globs: **/*.tsx
alwaysApply: false
---

# React Rules

- 함수형 컴포넌트를 사용한다.
- 재사용 로직은 custom hook으로 분리한다.
- 컴포넌트와 관련된 스타일/테스트는 가까운 위치에 둔다.
```

추천 방식은 `.cursor/rules/` 아래에 목적별로 나누는 겁니다.

```text
.cursor/rules/
  project-standards.mdc
  typescript-style.mdc
  react-patterns.mdc
```

작성 팁은: 한 파일에 한 주제만, 50줄 안팎으로 간결하게, “무엇을 하지 말라”보다 “어떻게 하라”를 구체적으로 쓰는 게 좋습니다.

---

**User**

@.cursorrules 위 .cursorrules 파일의 tdd_rules 섹션을 채워줘.
  - red_phase: 테스트 먼저 작성, 실패 확인 후 다음 단계 진행 조건
  - green_phase: 최소 코드로만 테스트 통과, 이 단계에서 리팩터링 금지
  - refactor_phase: 기능 변경 없이 구조 개선, 커버리지 유지 조건
YAML 형식 유지. tdd_rules 블록만 출력해.


---

**Cursor**

```yaml
tdd_rules:
  red_phase:
    - "테스트를 먼저 작성한다."
    - "작성한 테스트가 실패하는 것을 확인한 뒤 다음 단계로 진행한다."
    - "실패 원인이 기대한 기능 미구현 때문인지 확인한다."
  green_phase:
    - "테스트를 통과시키기 위한 최소 코드만 작성한다."
    - "이 단계에서는 리팩터링을 하지 않는다."
    - "기존 동작을 변경하지 않고 작성한 테스트만 통과시킨다."
  refactor_phase:
    - "기능 변경 없이 코드 구조만 개선한다."
    - "리팩터링 후 모든 테스트가 계속 통과해야 한다."
    - "기존 테스트 커버리지를 유지한다."
```

보고할 문제점 없습니다.

**User**

위에서 만든 .cursorrules 뼈대의 빈 섹션을 모두 채워줘.
MagicSquare 프로젝트 기준으로 작성해.
각 섹션 작성 규칙:
code_style:
  - python_version: "3.10+"
  - style_guide: PEP8 엄격 준수
  - type_hints: 모든 함수 파라미터와 반환값에 필수
  - docstring: Google 스타일, 모든 public 메서드에 필수
  - max_line_length: 88 (Black 기준)
architecture:
  ECB 패턴 3 레이어를 각각 정의해줘:
  - boundary: 외부 입출력 담당 (UI, API, CLI)
  - control: 비즈니스 로직 담당
  - entity: 도메인 데이터 및 규칙 담당
  레이어 간 의존성 방향도 명시해줘.
tdd_rules:
  지금은 문자열 1줄인데, 하위 항목으로 세분화해줘.
  각 phase마다:
    - description: 단계 설명
    - rules: 지켜야 할 규칙 목록
    - must_not: 이 단계에서 하면 안 되는 것
testing:
  - framework: pytest
  - pattern: AAA (Arrange-Act-Assert)
  - coverage_minimum: 80%
  - fixture_scope: 규칙 정의
  - naming_convention: test_ 접두사 필수
forbidden:
  항목마다 아래 구조로 작성:
    pattern: 금지 패턴
    reason: 금지 이유
    alternative: 대신 써야 할 것
  최소 포함 항목: print(), 하드코딩 상수, except 단독 사용
file_structure:
  ECB 기준 폴더 구조를 트리 형태 주석으로 작성해줘.
  boundary/, control/, entity/, tests/ 포함.
ai_behavior:
  Cursor AI가 코드 생성 전·중·후에 반드시 따라야 할 규칙.
  최소 포함:
    - 코드 작성 전 관련 테스트 파일 확인
    - ECB 레이어 경계 위반 금지
    - 타입힌트 없는 함수 생성 금지
    - tdd_rules 위반 시 경고 출력
완성된 .cursorrules 전체 파일을 출력해줘.

**Cursor**

요청하신 기준으로 `.cursorrules` 전체를 채우고 실제 파일도 업데이트하겠습니다. 먼저 프로젝트 구성을 간단히 확인해서 MagicSquare에 맞게 과하게 일반화하지 않도록 보겠습니다.

현재 프로젝트는 Python 기반이고 `entity/`, `tests/` 중심으로 시작된 상태입니다. `pyproject.toml`과 기존 테스트를 확인한 뒤 그 구조에 맞춰 규칙을 채우겠습니다.

기존 코드가 Python 3.10+, pytest, ECB/TDD 설명을 이미 `pyproject.toml`에 담고 있어서 그 방향에 맞춥니다. 이제 `.cursorrules` 전체를 요청한 구조로 갱신하겠습니다.

파일 업데이트는 완료했습니다. 마지막으로 수정된 `.cursorrules`에 IDE 진단이 생겼는지 확인하겠습니다.

`.cursorrules` 파일을 업데이트했고, IDE 진단상 오류는 없습니다.

```yaml
################################################################################
project:
  name: "MagicSquare"
  language: "Python"
  description: "Python 매직 스퀘어 도메인 프로젝트"
  methodology:
    - "ECB 아키텍처를 따른다."
    - "TDD 흐름으로 기능을 구현한다."
    - "도메인 규칙은 entity 계층에 명확히 둔다."

################################################################################
code_style:
  python_version: "3.10+"
  style_guide: "PEP8 엄격 준수"
  type_hints: "모든 함수 파라미터와 반환값에 필수"
  docstring: "Google 스타일, 모든 public 메서드에 필수"
  max_line_length: 88

################################################################################
architecture:
  pattern: "ECB"
  layers:
    boundary:
      responsibility: "외부 입출력 담당"
      examples:
        - "UI"
        - "API"
        - "CLI"
      must_not:
        - "도메인 규칙을 직접 구현하지 않는다."
        - "entity 내부 상태를 임의로 변경하지 않는다."
    control:
      responsibility: "비즈니스 로직 담당"
      examples:
        - "use case"
        - "application service"
        - "workflow orchestration"
      must_not:
        - "외부 입출력 세부 구현에 직접 의존하지 않는다."
        - "프레임워크 전용 코드를 포함하지 않는다."
    entity:
      responsibility: "도메인 데이터 및 규칙 담당"
      examples:
        - "domain entity"
        - "value object"
        - "domain invariant"
      must_not:
        - "boundary 계층에 의존하지 않는다."
        - "control 계층에 의존하지 않는다."
  dependency_direction:
    - "boundary -> control -> entity"
    - "entity는 다른 ECB 계층에 의존하지 않는다."
    - "control은 entity에 의존할 수 있지만 boundary에 의존하지 않는다."
    - "boundary는 control을 호출하고 외부 입출력 변환만 담당한다."

################################################################################
tdd_rules:
  red_phase:
    description: "구현 전에 실패하는 테스트를 먼저 작성하는 단계"
    rules:
      - "요구사항을 검증하는 테스트를 먼저 작성한다."
      - "작성한 테스트가 실패하는 것을 확인한 뒤 다음 단계로 진행한다."
      - "실패 원인이 기대한 기능 미구현 때문인지 확인한다."
    must_not:
      - "테스트 없이 기능 코드를 먼저 작성하지 않는다."
      - "테스트 실패를 확인하지 않고 green_phase로 넘어가지 않는다."
  green_phase:
    description: "실패한 테스트를 통과시키기 위한 최소 구현 단계"
    rules:
      - "테스트를 통과시키기 위한 최소 코드만 작성한다."
      - "기존 동작을 불필요하게 변경하지 않는다."
      - "새로 작성한 테스트와 기존 테스트가 통과하는지 확인한다."
    must_not:
      - "이 단계에서는 리팩터링을 하지 않는다."
      - "미래 요구사항을 예상한 일반화 코드를 작성하지 않는다."
  refactor_phase:
    description: "기능 변경 없이 구조와 가독성을 개선하는 단계"
    rules:
      - "기능 변경 없이 코드 구조만 개선한다."
      - "리팩터링 후 모든 테스트가 계속 통과해야 한다."
      - "기존 테스트 커버리지를 유지한다."
    must_not:
      - "리팩터링 중 새로운 기능을 추가하지 않는다."
      - "테스트를 약화하거나 삭제해서 통과시키지 않는다."

################################################################################
testing:
  framework: "pytest"
  pattern: "AAA (Arrange-Act-Assert)"
  coverage_minimum: "80%"
  fixture_scope:
    function: "테스트 간 상태 공유가 없어야 하는 기본 범위"
    class: "같은 테스트 클래스 안에서만 공유해도 안전한 경우"
    module: "모듈 전체에서 생성 비용이 큰 읽기 전용 fixture에만 사용"
    session: "프로젝트 전체에서 불변이고 외부 상태를 바꾸지 않는 fixture에만 사용"
  naming_convention:
    test_files: "test_ 접두사 필수"
    test_functions: "test_ 접두사 필수"
    test_methods: "test_ 접두사 필수"
  requirements:
    - "각 테스트는 Arrange-Act-Assert 흐름이 드러나야 한다."
    - "도메인 규칙은 entity 테스트에서 우선 검증한다."
    - "새 기능에는 관련 테스트를 함께 추가한다."

################################################################################
forbidden:
  - pattern: "print()"
    reason: "테스트 출력과 애플리케이션 입출력을 오염시키고 로깅 정책을 우회한다."
    alternative: "필요한 경우 logging을 사용하거나 테스트에서는 assertion으로 검증한다."
  - pattern: "하드코딩 상수"
    reason: "도메인 규칙 변경 시 중복 수정과 불일치를 유발한다."
    alternative: "의미 있는 이름의 모듈 상수나 설정 값으로 분리한다."
  - pattern: "except:"
    reason: "예상하지 못한 예외까지 삼켜 결함 원인을 숨긴다."
    alternative: "구체적인 예외 타입을 명시하고 필요한 경우 다시 raise한다."

################################################################################
file_structure:
  # MagicSquare_13/
  #   boundary/
  #     __init__.py
  #     cli.py
  #   control/
  #     __init__.py
  #     use_cases.py
  #   entity/
  #     __init__.py
  #     magic_square.py
  #     user.py
  #   tests/
  #     boundary/
  #     control/
  #     entity/
  expected_directories:
    - "boundary/"
    - "control/"
    - "entity/"
    - "tests/"
  rules:
    - "boundary 코드는 외부 입력을 control 호출에 필요한 형태로 변환한다."
    - "control 코드는 use case 단위로 entity를 조합한다."
    - "entity 코드는 도메인 데이터와 불변식을 포함한다."
    - "tests 폴더는 대상 계층 구조를 반영한다."

################################################################################
ai_behavior:
  before_coding:
    - "코드 작성 전 관련 테스트 파일을 먼저 확인한다."
    - "요구사항이 모호하면 구현 전에 확인 질문을 한다."
    - "변경 대상이 속한 ECB 계층을 먼저 판단한다."
  during_coding:
    - "ECB 레이어 경계를 위반하지 않는다."
    - "타입힌트 없는 함수를 생성하지 않는다."
    - "public 메서드에는 Google 스타일 docstring을 작성한다."
    - "tdd_rules를 위반해야 하는 상황이면 먼저 경고를 출력한다."
  after_coding:
    - "관련 pytest 테스트 실행을 우선 제안하거나 수행한다."
    - "테스트 실패 시 실패 원인을 설명하고 TDD 단계에 맞게 수정한다."
    - "리팩터링 후 기능 변경이 없었는지 확인한다."
```

**User**

.cursorrules를 읽고
MagicSquare의 User 엔티티 클래스를 ECB 패턴으로 작성해줘.
타입힌트, Google docstring, pytest 테스트 파일도 함께 만들어줘.


---
